1. PROJECT OVERVIEW
--------------------------------------------------------------------------------
• Project Name: RideCast
• Domain: Smart Urban Mobility, Intelligent Transportation Systems (ITS), Applied AI
• Target Region/Context: Coimbatore Urban Bus Transit Network (TNSTC - Tamil Nadu State Transport Corporation)
• Core Goal: Predict public bus passenger crowding in advance using deep learning time-series forecasting, and provide an automated decision-support engine for transport authorities to dispatch idle buses dynamically before congestion occurs.
• Key Beneficiaries:
  1. Passengers / Commuters: Get advance visibility into bus crowd levels (Low, Moderate, High) across all departure time slots to plan comfortable, stress-free journeys.
  2. Transport Authorities / Depot Managers: Receive automated crowd surge alerts, AI-driven explanations for demand spikes, smart fleet recommendations based on GPS proximity, and 1-click executive intelligence reports.

--------------------------------------------------------------------------------
2. PROBLEM STATEMENT & MOTIVATION
--------------------------------------------------------------------------------
• Challenges in Traditional Transit Systems:
  1. Static Bus Scheduling: Fixed timetables fail to adapt to real-time anomalies (e.g., sudden rainfall shifting commuters from two-wheelers to buses, weekend festival rushes, Monday morning office peaks).
  2. Overcrowding & Safety Hazards: Severe crowding during peak hours leads to passenger discomfort, delayed boarding/alighting, and reduced transit efficiency.
  3. Inefficient Fleet Utilization: Spare/idle buses sit at depots while specific arterial corridors suffer severe shortages.
  4. Information Gap: Commuters have no prior visibility into bus crowd conditions, leading to crowded stops and long wait times.

• The RideCast Solution:
  RideCast bridges this gap with a dual-portal architecture:
  - Predictive Visibility for Passengers (forecasts crowd density across 6 daily time slots with visual heatmaps).
  - Prescriptive Fleet Management for Authorities (predicts route-level deficits, ranks nearest idle buses using Haversine distance formulas, and records dispatch audit logs).

5. MACHINE LEARNING & FORECASTING ENGINE
--------------------------------------------------------------------------------

A. Model Architecture:
  • Model Type: Stacked LSTM (Long Short-Term Memory) Recurrent Neural Network
  • Input Shape: `(batch_size, 7, 16)` -> 7-day lookback sequence across 16 feature variables
  • Network Topology:
    1. LSTM Layer 1: 64 hidden units, return_sequences=True (captures multi-day temporal dependencies)
    2. Dropout Layer 1: Rate = 0.20 (prevents co-adaptation and overfitting)
    3. LSTM Layer 2: 32 hidden units, return_sequences=False (condenses high-level temporal representations)
    4. Dropout Layer 2: Rate = 0.20
    5. Dense Layer 1: 16 neurons, Activation = ReLU (non-linear feature combination)
    6. Dense Output Layer: 2 neurons, Activation = Linear (outputs Inbound & Outbound passenger counts)

B. The 16 Input Features:
  1. `time` (Encoded time slot)
  2. `service_id` (Categorical route code)
  3. `from_stop_id` (Encoded origin stop)
  4. `to_stop_id` (Encoded destination stop)
  5. `temperature_c` (Ambient temperature in Celsius)
  6. `humidity` (Relative humidity percentage)
  7. `rain_mm` (Rainfall precipitation in millimeters)
  8. `weather_code` (Categorical weather condition)
  9. `holiday` (Binary flag: 1 = Holiday / 0 = Regular day)
  10. `day_of_week` (0 = Monday, ..., 6 = Sunday)
  11. `inbound_scheduled_trips_per_day`
  12. `outbound_scheduled_trips_per_day`
  13. `inbound_passenger_count` (Historical lag)
  14. `outbound_passenger_count` (Historical lag)
  15. `month` (1 to 12)
  16. `day_of_year` (1 to 366 for seasonality)

C. Model Training & Evaluation Metrics:
  • Loss Function: Mean Squared Error (MSE)
  • Optimizer: Adam (adaptive learning rate)
  • Primary Evaluation Metric: Mean Absolute Error (MAE)
  • Historical Inference Confidence: 94.6% accuracy score
  • Low MAE (< 4-5 passengers per departure trip) ensuring reliable deployment.

D. Explainable AI (XAI) Reason Generator:
  RideCast translates raw numerical predictions into human-readable operational drivers:
  - Weekday office/school rush hours (08:00–10:00 & 17:00–19:30)
  - Weekend shopping traffic surges (commercial zones like Gandhipuram / Town Hall)
  - Weather modal shifts (monsoon/heavy rain causes two-wheeler users to take public buses)
  - Major arterial corridor transfer bottlenecks

6. SMART FLEET ALLOCATION & DISPATCH ALGORITHM
--------------------------------------------------------------------------------

Step 1: Surge Detection
  - For target date and route, total predicted passengers ($P_{exp}$) is compared against baseline capacity ($C_{norm}$).
  - Surge Ratio $R = \frac{P_{exp}}{C_{norm}}$
  - Classification:
    • $R < 0.85$  -> Crowd: "Low" 🟢 (No extra buses needed)
    • $0.85 \le R \le 1.05$ -> Crowd: "Moderate" 🟡 (0 to 1 buffer bus)
    • $R > 1.05$  -> Crowd: "High" 🔴 (Deficit = $P_{exp} - C_{norm}$; Extra Buses = $\lceil \text{Deficit} / 50 \rceil$)

Step 2: Proximity-Based Bus Recommendation (Haversine Formula)
  - System identifies all buses currently marked as "Idle" in `bus_availability.csv`.
  - For each idle bus at depot location $(\phi_1, \lambda_1)$, it calculates great-circle distance to route starting terminus $(\phi_2, \lambda_2)$:
      $a = \sin^2\left(\frac{\Delta\phi}{2}\right) + \cos(\phi_1)\cos(\phi_2)\sin^2\left(\frac{\Delta\lambda}{2}\right)$
      $c = 2 \cdot \text{atan2}\left(\sqrt{a}, \sqrt{1-a}\right)$
      $d = R \cdot c \quad (R = 6371.0\text{ km})$
  - Filters by seat capacity ($\ge 50$ seats).
  - Ranks idle buses by lowest dispatch distance (Deadhead km minimization).
  - Automatically recommends the top-ranked bus.

Step 3: 1-Click Dispatch Execution
  - Authority officer clicks "Confirm Allocation".
  - Backend updates bus status from "Idle" to "Allocated", writes entry to SQLite `allocations` table with reason, officer name, and timestamp.

7. DETAILED END-TO-END FLOWS (FOR USER JOURNEYS)
--------------------------------------------------------------------------------

A. PASSENGER USER FLOW:
  1. Passenger opens RideCast web portal (Default: Passenger Portal).
  2. Selects Origin Stop (e.g., 'Ukkadam') and Destination Stop (e.g., 'Saibaba Colony').
  3. Selects Travel Date from the Interactive Calendar and chooses a Departure Time Slot (e.g., 08:00 - 10:00).
  4. Clicks "Forecast Crowd Density".
  5. The system returns:
     - Inbound & Outbound passenger counts.
     - Visual Crowd Badge: Low 🟢, Moderate 🟡, High 🔴.
     - Seat Occupancy Percentage.
     - 6-Slot Time Heatmap (allows commuter to choose a less crowded slot).
     - Interactive Leaflet Route Map showing traversed stops and route polyline.
  6. Passenger can submit feedback ("Was this prediction accurate?").

B. TRANSPORT AUTHORITY USER FLOW:
  1. Officer navigates to "Authority Portal" and completes secure credentials login.
  2. Officer Profile View displays officer badge, active division (Coimbatore), and daily statistics.
  3. Navigates to "Network Forecast":
     - Selects Target Date and Route (or "All Routes").
     - Views Executive KPIs (Total Expected Passengers, Baseline Capacity, Crowd Ratio %, Extra Buses Required).
     - Inspects Route Intelligence Cards containing crowd badges and XAI surge factors.
  4. If a route is under high crowd alert (🔴), officer opens "Smart Allocation":
     - System displays ranked idle buses from nearby depots with exact deadhead distances (e.g., Ukkadam Depot - 1.2 km).
     - Officer reviews recommended bus and clicks "Allocate Bus".
  5. Officer can review all dispatched buses in the "Allocation Audit Trail".
  6. Officer can click "Export Intelligence PDF" to instantly download a formatted A4 executive report for morning operational briefings.

8. BACKEND API DIRECTORY (REST ENDPOINTS)
--------------------------------------------------------------------------------

• Metadata & Network:
  - GET  `/api/stops`               : Returns all transit stops with lat/long coords.
  - GET  `/api/routes`              : Returns all monitored route definitions.
  - GET  `/api/services-between`    : Returns valid service IDs connecting two stops.
  - GET  `/api/timetable/{sid}`     : Returns departure schedule for a service.
  - GET  `/api/time-slots`          : Returns the 6 operational time slots.
  - GET  `/api/map/data`            : Full network GIS data (polylines, coordinates, colors).

• AI Prediction:
  - POST `/api/predict/demand`      : Single slot inference (Inbound/Outbound counts, crowd level).
  - POST `/api/predict/all-slots`   : 6-slot batch inference for passenger heatmap grid.

• Authority & Fleet Operations:
  - GET  `/api/authority/overview`        : Aggregated network KPIs & multi-route forecasts.
  - GET  `/api/authority/route/{sid}`     : Deep-dive forecast for single route.
  - GET  `/api/authority/recommendations` : Ranks idle buses nearest to route start.
  - POST `/api/authority/allocate`        : Dispatches an idle bus and writes audit log.
  - GET  `/api/authority/allocations`     : Retrieves full dispatch history from database.
  - GET  `/api/authority/fleet`           : Retrieves live inventory of all buses & statuses.
  - GET  `/api/authority/export-pdf`      : Generates & streams formal ReportLab A4 PDF report.

• Auth & Feedback:
  - POST `/api/auth/login`          : Verifies authority credentials and issues session token.
  - POST `/api/feedback/submit`     : Submits passenger prediction feedback.
  - GET  `/api/feedback/list`       : Lists recorded feedback.
